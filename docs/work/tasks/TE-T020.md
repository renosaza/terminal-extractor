# Explicit human/agent handoff и geometry ownership

## Результат

Проверить и реализовать режим одного writer, локальный Take control и primary user view как источник rows/cols.

## Приёмка

При agent control все зарегистрированные human attach-clients либо реально read-only, либо exclusivity capability явно false. Возврат управления доступен локально без модели; queued agent input отменён. MCP control client не уменьшает размеры user pane. Не обещать automatic key takeover без event source.

## Проверка

NOT_RUN: два user clients, два agents, resize обоих views, Stop при длинном dispatch, последняя view закрыта. Измерить revoke latency и границу уже доставленных bytes. AT-10/12/15, TE-C03/07.

PARTIAL private tmux feasibility, 2026-09-25: `python3 -B probes/tmux/read_only_clients.py` и `python3 -O -B probes/tmux/read_only_clients.py` прошли на установленном tmux 3.7c. В отдельном private socket с `/dev/null` config два синтетических PTY-клиента подключились к одной временной pane; `client_readonly` сообщил `0` и `1` для обычного и `attach-session -f read-only,ignore-size`. Два синтетических ввода обычного клиента достигли fixture-процесса, ввод read-only клиента между ними не достиг его; содержимое pane не выводилось. Дополнение: обычный PTY 80×24 установил размер tmux window, после подключения read-only PTY 20×10 с `ignore-size` размер остался 80×24; status line в private fixture отключена для точного сравнения. Probe не подключал Ghostty/Terminal.app, не использовал пользовательский tmux и очищал только свой namespace. Это проверка механики одного read-only attach и одной geometry policy, не гарантия для всех клиентов и не product handoff: локальный Take control, grant/revoke, queued agent input, GUI resize и `exclusive_input_enforced` остаются `NOT_RUN`/`false`.
