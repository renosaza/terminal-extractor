# Подтвердить stack и границу первого релиза

## Результат

Минимальный Swift MCP stdio прототип и tmux capture proof; таблица реальных SDK/protocol/macOS/tmux versions; обновлённый proposed ADR с evidence.

## Приёмка

Version negotiation работает с выбранным client, structured output bounded. Проверена возможность capture-before-shell, screen state и отдельного tmux namespace. Выбраны проверяемые dependency pins и minimum versions. Native blockers не скрываются переходом на managed; принимается точный release scope без ложного full Existing.

## Проверка

PARTIAL: stdio start/stop и SDK/tool schema roundtrip, isolated tmux capture и screen text прошли; длинная output stream, GUI attach и два реальных MCP-клиента — `NOT_RUN`. Не добавлять cloud/DB service. AT-12/17, TE-C01..04/06/08.

## Фактический результат и продолжение

На стенде macOS 27.0 (26A428, Apple M5) доступен Swift 6.4. По разрешению владельца Homebrew установил tmux 3.7c с libevent 2.1.13 и jemalloc 5.4.0. Официальный [Swift MCP SDK 0.12.1](https://github.com/modelcontextprotocol/swift-sdk/releases/tag/0.12.1), commit `a0ae212ebf6eab5f754c3129608bc5557637e605`, закреплён в [Package.swift](../../../probes/mcp/Package.swift) и [Package.resolved](../../../probes/mcp/Package.resolved) проектного probe. Зависимости SwiftPM загружены только в `.build` проекта.

`swift build --package-path probes/mcp -c release` прошёл. `python3 probes/mcp/check.py` запустил stdio server, запросил protocol `2026-07-28`, получил negotiated `2025-11-25`, прочитал tool schema и получил bounded `structuredContent` на 100000 байт входа; server завершился после закрытия stdin. `sh probes/tmux/probe.sh` прошёл на отдельном socket с `/dev/null` config: `pipe-pane` включён до запуска тестовой команды, её текст обнаружен и в stream file, и в `capture-pane`; pane сообщил размер 80×24. Ручной fixture из TE-T017/TE-T018 позднее подтвердил временный attach private tmux shell к явно выбранной тестовой Ghostty pane и markers screen/pipe; product GUI binding по-прежнему `NOT_RUN`. Эти проверки доказывают узкий механизм, не полноту stream под нагрузкой и не привязку к видимому окну.

Повторная локальная проверка 2026-09-24 расширила тот же private probe двумя tmux sessions: после закрытия первой по точному имени `=te-probe` вторая сохранила прежние pane ID и PID; `sh probes/tmux/probe.sh` — PASS. Проверка сначала выявила, что `has-session -t te-probe` сопоставляет префикс и находит `te-probe-other`; точный target обязателен для lifecycle. Пользовательский tmux server/config и открытая Ghostty pane не затрагивались. Это feasibility evidence, не продуктовый backend или GUI binding.

TE-T001..003 ещё не закрыты, поэтому release scope и minimum app versions не утверждены. Следующий шаг — проверить длинный output, GUI attach и реальные клиенты после решения native gates. Проверенный revision: ветка `te-e01` от `5a6aa0e` плюс текущие изменения.
