# Managed recorder и authoritative screen

## Результат

Подключить выбранный pipe/control stream до запуска shell, читать screen state из tmux, выдавать offsets/watermarks и capture epochs.

## Приёмка

Нет чтения TTY slave как лога и смешивания control-command completion с shell completion. Запуск/перезапуск recorder отражает gaps. Screen geometry/cursor/attributes передаются только при доступности. Один terminal-query responder; normalized view не отвечает приложению повторно.

## Проверка

PARTIAL (224813e): `python3 probes/tmux/bounded_capture.py` и `python3 -O probes/tmux/bounded_capture.py` — PASS для готовности private `pipe-pane -O` до синтетической нагрузки, точного PTY byte corpus и маркировки gap при квоте 64 байта. Probe создаёт только отдельную detached `/bin/sleep` pane в private tmux namespace; выбранную пользовательскую pane не читает. `clean_eof` означает лишь завершение pipe без замеченной этим sink потери, не непрерывность записи и не `complete_for_interval`.

PARTIAL owner gate: private `termex-capture-sink` и `ManagedTmux.armCapture` проверены на readiness/foreign-pipe refusal в detached fixture. `swift run TermexCaptureSinkCheck` подтвердил точный synthetic byte corpus, quota gap и clean EOF самого Swift sink; product recorder, offsets/watermarks и capture epoch остаются `NOT_RUN`.

PARTIAL metadata observation, 2026-09-24: `captureObservation` в owner возвращает текущий размер private segment и flags без его содержимого; проверены начальный нулевой размер, живой pipe и отказ cross-session/после close. Отдельный synthetic workload после gate найден в private segment fixture; проверка не возвращала его через API. Позднейший fixture TE-T017 подтвердил положительный размер и quota gap через owner API, но это не durable offset. Sink создаёт `clean_eof` после `fsync` и закрытия segment FD, но marker и каталог не синхронизируются как recovery manifest. Sealed durable watermark, restart/gap manifest и product API остаются `NOT_RUN`.

PARTIAL fail-closed gap marker, 2026-09-25: если sink замечает потерю байтов, но не может создать private `gap` marker, он теперь завершает процесс с ошибкой вместо продолжения drain с подключённым pipe и ложным `gapObserved=false`. `swift build --product termex-capture-sink` и `swift run TermexCaptureSinkCheck` проверили отказ создания marker после ready в private каталоге без права записи, код выхода 1 и отсутствие `clean_eof`; обычные exact bytes/quota gap/clean EOF сохранились. Позднейший private owner fixture довёл тот же отказ до `captureObservation`: segment ограничен 4096 байтами, `gapObserved=false`, `sinkClosedCleanly=false`, `pipeConnected=false`, а `revalidate` отвергает прежнюю привязку. tmux при этом продолжал показывать прежний `pane_pipe_pid` после смерти sink. Owner теперь сверяет PID и время старта sink, а не только наличие PID; реальный повтор PID не воспроизводился. Это точечное обнаружение отказа, не защита от гонки после проверки; устойчивость к ошибке диска и durable coverage manifest не проверены. Это не product recorder.

PARTIAL tmux screen metadata, 2026-09-25: `ManagedTmux.screenMetadata` возвращает только размеры сетки, позицию курсора и флаг alternate screen для явной private `SessionRef`/generation после проверки pane и capture pipe. На установленном tmux 3.7c `swift run TermexManagedTmuxCheck` проверил resize 93×27, вход/выход из alternate screen в синтетической private zsh pane и отказ stale generation/pane и dead sink. Это моментальный snapshot без текста, атрибутов, гарантии согласования с byte stream и без product read/grant API; authoritative screen и полная TE-T019 приёмка остаются открытыми.

PARTIAL sink close record, 2026-09-25: после EOF и `fsync` private segment sink записывает число сохранённых байтов и `clean`/`gapped` в `closed.pending`, синхронизирует файл, переименовывает в `closed` и синхронизирует каталог. `swift run TermexCaptureSinkCheck` проверил synthetic clean/quota-gap записи, отсутствие `closed` при отказе создать marker и прерывании до EOF, а также отсутствие оставшегося `.pending` в этих случаях. `swift run TermexVisibleOwnerCheck --self-check` дополнительно сверил `closed clean` с размером private segment после owner-backed закрытия tmux pane. Пользователь затем запустил этот revision в выбранной тестовой Ghostty pane и сообщил `private_owner=PASS`, `capture_pipe_marker=PASS`, `screen_metadata=PASS`, `clean_fixture_close=PASS`, `attach_return=PASS`; fixture возвращает эти статусы только после проверки записи `closed clean` и размера segment. Это не независимая проверка присланных статусов и не захват исходной истории Ghostty. На этом revision запись проверял только fixture, не product read API; session/generation/epoch и restart reconciliation отсутствовали. Сбой после rename до directory `fsync`, сбой питания и отказ диска не воспроизводились; наличие `closed` без проверки не доказывает durable watermark или `complete_for_interval`. `closed clean` может существовать без legacy `clean_eof`, если создание последнего не удалось; их нельзя считать совместным подтверждением чистого завершения.

PARTIAL owner post-close check, 2026-09-25: `ManagedTmux.closedCaptureObservation` теперь после точного `close` принимает только сохранённый `SessionRef`/generation/capture gate, сверяет private directory и segment identity, размер segment с короткой записью `closed` и непротиворечивость `gap`/`clean_eof`; возвращает только число байтов и gap flag. Отсутствующая запись/ещё не созданный `clean_eof` дают `nil`, повреждённая запись или конфликт marker — ошибку, не ложную полноту. `swift run TermexManagedTmuxCheck` проверил clean и quota-gapped закрытие, отказ чужого gate; `swift run TermexVisibleOwnerCheck --self-check` проверил реальный owner-backed close, stale generation, повреждённую/отсутствующую запись и конфликт marker. Фокусная независимая проверка нашла гонку чтения размера до появления `closed` и принятие `clean` вместе с `gap`; оба замечания исправлены до этих проверок. Пользователь затем запустил новый fixture в выбранной тестовой Ghostty pane и сообщил `private_owner=PASS`, `capture_pipe_marker=PASS`, `screen_metadata=PASS`, `clean_fixture_close=PASS`, `attach_return=PASS`; fixture выдаёт эти статусы после вызова owner post-close API. Это пользовательский отчёт о live результате, не проверка произвольного терминального содержимого. Путь всё ещё не подключён к product host/грантам, не содержит capture epoch и не переживает restart owner. Это не durable watermark и не `complete_for_interval`.

NOT_RUN: product recorder, session/generation/epoch/offsets, authoritative screen, split UTF-8 через границы чтения, CR/erase/alt screen semantics, slow consumer, burst, recorder restart, initial scrollback overlap. AT-04/08/12/15 и полная TE-C01/04/05 приёмка остаются открытыми.
